# AGENTS.md

## Registro obligatorio de cambios

### Cuándo registrar

Cada vez que modifiques archivos del proyecto, actualiza `CAMBIOS_AGENT.md`.

El registro debe documentar cambios de código de forma literal. No debe ser un resumen general.

No termines una tarea que haya modificado archivos sin actualizar `CAMBIOS_AGENT.md`.

Agrupa todos los cambios de una misma tarea/sesión en una sola entrada, con un bloque por cambio. No crees una entrada nueva por archivo ni por edición individual.

### Estructura de la entrada

Cada entrada debe añadirse al **principio** del archivo (las más recientes arriba) y debe incluir:

- Título con formato `## AAAA-MM-DD HH:MM - <título breve>` (la fecha y hora en el título sirven como identificador único de la entrada).
- Lista de archivos modificados, inline tras el título: `**Archivos modificados:** ruta1, ruta2`. Si hay 10 o más archivos, usa lista con guiones.
- Un bloque `### Cambio N - <nombre>` por cada cambio relevante.

El `<título breve>` debe:

- Empezar con un verbo en infinitivo (`Añadir`, `Corregir`, `Refactorizar`, `Eliminar`, `Renombrar`).
- Tener menos de 60 caracteres.
- Describir el resultado, no el proceso ni el estado del trabajo.
- Evitar palabras vacías como `varios`, `actualizaciones`, `cambios`, `WIP`, `fix`, `tmp`.

### Contenido de cada cambio

Cada bloque de cambio debe incluir tres apartados:

- **Código anterior**: el fragmento exacto que existía antes del cambio.
- **Código nuevo**: el fragmento exacto que quedó después del cambio.
- **Por qué se cambió**: el motivo concreto de sustituir el código anterior por el nuevo.

Si el cambio es código que antes no existía (componente, función, constante, tipo, helper, estilo, bloque o asset nuevo), regístralo como cambio independiente y usa como `Código anterior` literalmente: `` `No existía <nombre del bloque> en <archivo>.` ``

No documentes solo dónde se usa el código nuevo. Documenta también la creación del bloque nuevo.

Si no puedes verificar el código anterior literal (porque no tienes acceso al diff o al archivo previo), indícalo en la entrada con la línea `Código anterior no verificable: <motivo>` en lugar de inventarlo.

Si dentro de la misma sesión modificas un mismo fragmento varias veces, mantén `Código anterior` fijo en el estado inicial de la sesión y actualiza `Código nuevo` a medida que avances. Los valores intermedios no se documentan.

Las entradas de sesiones anteriores ya cerradas no se modifican. Si vuelves a tocar un fragmento en una sesión posterior, crea una entrada nueva: su `Código anterior` será el estado actual (que coincide con el `Código nuevo` de la entrada anterior).

### Idioma

Escribe las entradas en español.

## Excepciones

Estos casos no se documentan en `CAMBIOS_AGENT.md` porque git ya los gestiona y son inviables en texto:

- Archivos binarios (imágenes, fuentes, PDFs, audio).
- Lockfiles (`package-lock.json`, `yarn.lock`, `pnpm-lock.yaml`).
- Carpetas autogeneradas (`dist/`, `build/`, `.next/`, snapshots de tests).
- Archivos autogenerados por Capacitor cuyo encabezado declara `DO NOT EDIT THIS FILE! IT IS GENERATED EACH TIME "capacitor update" IS RUN` (`android/app/capacitor.build.gradle`, `android/capacitor.settings.gradle` y equivalentes). Se regeneran con `npx cap sync`.
- El propio `AGENTS.md` y el propio `CAMBIOS_AGENT.md`: los cambios sobre estos archivos no se autodocumentan (evita bucles).

Para revertir cualquiera de estos, usa `git checkout` directamente sobre el archivo.

## Ejemplo de entrada

Así debe verse una entrada bien formada en `CAMBIOS_AGENT.md`:

````md
## 2026-05-17 14:30 - Cambiar color del botón principal

**Archivos modificados:** `src/styles/theme.ts`

### Cambio 1 - Color del botón

#### Código anterior
```ts
button: {
  color: 'red',
  padding: 8,
}
```

#### Código nuevo
```ts
button: {
  color: 'blue',
  padding: 8,
}
```

#### Por qué se cambió
El rojo no contrastaba bien con el fondo claro. Azul mejora accesibilidad.
````

Notas sobre el formato:

- La fecha vive solo en el título (`##`), no se repite debajo.
- `Archivos modificados` va inline tras el título. Si hay muchos archivos (10+), usa lista con guiones.
- El lenguaje del fence (` ```ts `, ` ```py `, etc.) debe coincidir con el del archivo modificado.
